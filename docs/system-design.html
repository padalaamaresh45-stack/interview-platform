01 · Criterion A

Rationale for Proposed Solution

A client–server web application is the right architectural pattern for this problem because the system naturally splits along role boundaries — an admin configuring positions and questions, an interviewer consuming and scoring them — that map cleanly onto separate, reusable interface and route modules. Keeping business rules (session checks, score validation, atomic submission) on the server means every client sees the same enforced behaviour, rather than duplicating validation logic across screens.

My choice of language for the backend is Python, using the FastAPI framework, because of the strength of its ecosystem for exactly this kind of data-driven service: SQLAlchemy for structured, typed database access, Pydantic for request/response validation that rejects malformed input before it reaches business logic, and passlib for password hashing rather than rolling my own. I chose Visual Studio Code as my IDE for this project, as its integrated debugger, inline type-checking, and REST client extensions let me step through request handling and inspect state directly, rather than debugging through print statements.

My choice of database management system is PostgreSQL, as it is a mature, open-source relational database that enforces the data integrity this system depends on directly at the schema level — a CHECK constraint makes an out-of-range score physically impossible to store, and foreign keys guarantee a score can never reference a question that doesn't belong to the candidate's position. Through JOIN queries across candidates, questions, and interview_scores, the admin can retrieve a candidate's full scoring breakdown in a single query, and its transaction support is what makes the "submit all scores atomically" requirement actually guaranteed rather than merely likely.

Success Criteria

  1. The admin should be able to log in with a username and password.
  2. The interviewer should be able to log in with a username and password and see only the candidates assigned to them.
  3. The admin should be able to create a Position and add an ordered list of questions to it.
  4. The admin should be able to create a Candidate record and assign it to exactly one Position and one Interviewer.
  5. The interviewer should be able to view an assigned candidate's questions in the exact order set by the admin.
  6. The interviewer should be able to enter a score from 1–5 and an optional comment for every question.
  7. The interviewer should be able to submit all scores for a candidate in a single action, after which the candidate is marked completed.
  8. The system should reject any score entered outside the 1–5 range.
  9. A completed candidate should no longer appear in the interviewer's active queue.
  10. All data entered should remain stored correctly after the server restarts.
